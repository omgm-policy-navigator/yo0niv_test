# 시스템 아키텍처

## MVP 구성

MVP 시스템은 사용자 인터페이스, 백엔드 서비스, 정책 데이터 수집 파이프라인, 데이터 저장소로 나뉜다.

```text
사용자
→ React/Vite 프론트엔드
→ FastAPI 백엔드
→ PostgreSQL + pgvector
```

## 사용자 인터페이스

프론트엔드는 사용자가 분야를 선택하고 질문에 답하며, 정책 그래프와 챗봇 설명을 확인하는 화면을 담당한다.

주요 화면:

- 챗봇 인터페이스
- 정책 분야 선택
- 질문 흐름
- 정책 그래프
- 정책 상세
- 신청 로드맵
- 저장 정책 및 알림 설정

## 백엔드 서비스

FastAPI 백엔드는 API Gateway 역할과 함께 다음 서비스를 제공한다.

### 챗봇 & LLM 서비스

- 질문 흐름 관리
- 시스템 프롬프트 관리
- 사용자 대화 맥락 관리
- 정책·조건·행동 노드 설명 생성

MVP에서는 로컬 LLM 후보로 Llama 3 또는 Mistral을 고려한다.

### 정책 판정 서비스

- 사용자 조건과 정책 룰 비교
- 충족, 미충족, 미확인 조건 계산
- 정책 매칭 및 우선순위 점수 계산
- 판정 결과 저장

### RAG 서비스

- 사용자 질문 이해
- 관련 정책 문서 검색
- 공식 원문 기반 근거 생성
- 신청 조건, 서류, 절차, 유의사항 설명

### 공통 서비스

- 사용자 및 세션 관리
- 대화와 답변 기록
- 알림
- 로그와 모니터링

## 정책 데이터 수집 파이프라인

정책 데이터는 공공데이터 API와 공식 웹 문서에서 수집한다.

수집 후보:

- 보조금24
- 복지로
- 서울시 OpenAPI
- 공고문
- FAQ
- 안내 페이지

파이프라인 흐름:

```text
공공데이터 API / 공식 문서
→ 크롤링 또는 문서 수집
→ 정책 파싱 및 구조화
→ 관리자 검수
→ 데이터 저장소 반영
```

정책 파싱 단계에서는 JSON 변환과 조건 추출을 수행한다. 관리자 검수 단계에서는 자동 추출된 정책 조건과 원문 근거를 승인하거나 수정한다.

## 데이터 저장소

운영 데이터는 PostgreSQL에 저장한다.

저장 대상:

- 사용자 조건
- 정책
- 정책 룰
- 질문
- 정책 판정 결과
- 정책 관계
- 대화 및 답변 기록

정책 문서 임베딩은 PostgreSQL 확장인 pgvector에 저장한다.

저장 대상:

- FAQ
- 안내문
- 공고문
- 신청 조건 원문
- 필요 서류 원문

## 데이터 흐름

```text
1. 사용자가 챗봇에서 분야 선택 및 질문 응답
2. 응답을 user_fact로 저장
3. Rule Engine이 정책 판정 수행
4. RAG가 관련 문서 검색
5. LLM이 근거 기반 답변 생성
6. 정책 그래프 데이터 생성 후 프론트엔드에 전달
7. 사용자는 그래프에서 정책, 조건, 행동 선택
8. 챗봇 대화가 선택 노드 맥락으로 이어짐
```

## 기술 스택

| 영역 | 기술 |
| --- | --- |
| Frontend | React, Vite |
| Backend | Python, FastAPI |
| LLM | Llama 3 또는 Mistral |
| Embedding | bge-m3 또는 E5-base |
| Vector Store | pgvector |
| DB | PostgreSQL |
| Runtime | Docker 단일 서버 |

## 현재 레포의 책임

현재 레포는 FastAPI 백엔드 초기 구현을 담당한다.

포함:

- API 진입점
- Health Check
- 설정 로딩
- 구조화 로그
- 정책 도메인 어휘
- 테스트 구조
- 백엔드 아키텍처 문서
- 향후 프론트엔드와 인프라를 수용할 `frontend`, `infra` 경계

제외:

- React 프론트엔드 구현
- 실제 PostgreSQL 스키마와 마이그레이션
- 실제 LLM 연결
- 정책 수집 파이프라인 구현
- 관리자 검수 UI
